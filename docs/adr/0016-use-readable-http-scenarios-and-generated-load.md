# ADR-0016: Use readable HTTP scenarios and generated load targets

- Status: Accepted
- Date: 2026-09-04

## Context

The repository's focused Go tests cover domain, persistence, authentication,
and transport behavior, while the demo smoke check proves that the composed
process starts and handles representative requests. The smoke script is not a
simple request/response document, and it does not provide repeatable workload
generation or latency and status reports for sale offers, listings, and buys.

Every request also needs a short-lived assertion bound to its deterministic
protobuf request and, for mutations, its idempotency key. A useful load tool
must therefore receive a separately signed target for every generated
mutation rather than replaying one generic bearer token and body.

## Decision

Use Hurl files as executable REST request/response documentation. Supply
assertions as redacted secret variables generated by the development-only
issuer. Parse the custom active-offer JSON Text Sequence with `jq --seq` in
addition to the readable Hurl assertions.

Use Vegeta for HTTP workload execution and reporting. A development-only Go
command emits its JSON target format with unique request bodies, operation-
bound assertions, and idempotency keys. Pipe targets directly to Vegeta so
credentials are not retained with result artifacts.

Run both layers against the same isolated, migrated, seeded demo lifecycle.
Keep a small correctness-gated workload in `devenv test` and CI. Keep the
larger configurable load task manual, record its reports under `.artifacts`,
and do not enforce machine-dependent latency thresholds until the service has
a defined deployment profile and objectives.

Limit this first suite to the REST sale-offer creation, active-offer and
active-series listing, and buy endpoints. Existing smoke coverage continues to
check native gRPC health and the absence of runtime reflection; equivalent
gRPC business journeys can be added when they provide distinct evidence.

## Consequences

- The primary business interaction can be read without following shell control
  flow and is executed against the complete server and PostgreSQL adapter.
- Generated workloads cover distinct creates and buys, populated listings, and
  contention for one offer while respecting request-bound authentication.
- Local and CI setup remains reproducible through pinned Nix/devenv packages.
- The small CI workload catches generator, authentication, status-distribution,
  and teardown regressions but does not establish production capacity.
- Absolute performance comparisons require the same hardware and configuration
  until a production-like benchmark environment and objectives are defined.
- Hurl does not natively interpret the service's JSON Text Sequence as one JSON
  document, so a small stream-aware assertion remains in the shell runner.

## Alternatives considered

### Keep extending the curl smoke script

Curl and jq can exercise every response, but the surrounding token generation,
status handling, and lifecycle logic obscure the request/response examples.
The smoke check remains useful for composition while Hurl owns the readable
business journey.

### Write all end-to-end tests in Go

A Go suite would provide rich helpers and one language, but its setup and
assertion code would be less direct as API documentation. Go remains the right
place for the target generator because it can reuse the exact protobuf request
encoding used by authentication.

### Gate absolute latency in shared CI

An immediate latency threshold would be easy to automate but would measure the
variable hosted runner as much as the service. Status and cardinality are gated
now; performance thresholds wait for an explicit environment and objective.
